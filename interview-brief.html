Technical brief · built Aug 2026

TransitPulse BC

A streaming lakehouse that ingests Metro Vancouver's live bus feed and predicts arrival delay more accurately than the published schedule. What it does, what data feeds it, and what broke.

The one-sentence version

Every minute a Lambda pulls TransLink's GTFS-Realtime feed, flattens protobuf into one row per predicted stop arrival, and publishes to Kinesis. Two consumers read the same stream: Firehose batches it into S3 as Parquet for training, and a second Lambda maintains current delay state in DynamoDB for serving. A nightly Spark job collapses ~25 repeated predictions per arrival into a single labelled row, a quality gate decides whether that day is fit to train on, and an XGBoost model is scored against three baselines before it is allowed into the registry.

Data flow

Nine stages, two paths

Everything splits at Kinesis. One path answers how late is this bus right now in milliseconds; the other answers what patterns exist across millions of past arrivals. Neither can do the other's job.

1

Poller fetches

Two TransLink URLs return protobuf. The flattener emits one row per stop prediction, not per bus — a single bus with 30 upcoming stops becomes 30 rows.

every 60s · ~11,000–21,000 rows per poll

2

Write to Kinesis

500 records per PutRecords call, deliberately paced to stay under the shard's write ceiling.

~42 batches · throttled to 900 rec/sec

3

Firehose → S3 bronze

Buffers until 5 minutes or 64 MB, converts JSON to Parquet against a Glue schema, writes to raw/trip_updates/dt=…/hour=…/. Flushing every minute instead would create 1,440 tiny files a day and make every query slower.

batch path · ~5 min latency

4

Online features → DynamoDB

Reads the same records independently. Aggregates each batch in memory, then writes one item per route+stop. Items expire after two hours via TTL — no cleanup job, no storage creep.

live path · seconds

5

Silver — the hard one

The feed re-predicts the same arrival ~25 times as the bus approaches. This keeps the final observation plus snapshots of what was believed 5, 15, and 30 minutes earlier. MERGE INTO an Iceberg table so reruns update rather than duplicate.

nightly 02:20 UTC · 2,021,771 → 79,945 rows

6

Quality gate

Five rules: row count, key uniqueness, label completeness, delay bounds, trip_id completeness. Failure routes to quarantine, not crash — the gold layer is never rebuilt and the bad partition stays inspectable.

exits non-zero → Step Functions branches

7

Gold — point-in-time correctness

Adds weather, historical priors, and upstream delay propagation. Every feature must have been knowable 15 minutes before arrival. Historical aggregates use service dates strictly earlier than the run date.

the leakage guard

8

Train and gate

XGBoost on a spot instance, ~7 minutes. A ConditionStep rejects any model that fails to beat the persistence baseline by 8%. Registration and deployment are separate steps.

weekly · ~$0.01 per run

9

Serve

Three DynamoDB point reads build the feature vector, then a serverless SageMaker endpoint returns a prediction. The response includes feature_fill_rate so a caller knows how much rests on real data versus defaults.

~5 ms lookup · ~50 ms warm inference

Code

Three files to know cold

src/common/features.py — the contract

A model is a function from a feature vector to a number. If the vector built at training time and the vector built at serving time differ in order, null-handling, or units, the model degrades silently and nothing errors. The defence is one definition, imported by both paths.

# Order is load-bearing: XGBoost consumes a positional CSV row.
FEATURE_ORDER: tuple[str, ...] = (
    "hour_of_day", "day_of_week", "is_weekend", ...
)

# Both paths fill nulls identically. That is itself part of the contract.
DEFAULTS: dict[str, float] = { "hour_of_day": 12.0, ... }

A tuple, not a list — reordering silently changes what the model sees, and immutability makes that harder to do by accident. coerce() handles three kinds of missing: None, unparseable strings, and NaN. The NaN check is out != out, which looks like a typo and isn't.

src/glue/silver_stop_events.py — the hardest job

# Keep the last prediction received for each stop event.
window = Window.partitionBy(*KEY).orderBy(F.col("ingest_ts").desc())
updates.withColumn("rn", F.row_number().over(window)).where(F.col("rn") == 1)

The partition key includes start_date. Without it, the same trip_id recurring daily would collapse across days and merge Tuesday's bus with Wednesday's. snapshot_at() is the clever part: to predict 15 minutes ahead you need the state of the world 15 minutes before arrival, so it filters to predictions made at least that far out and picks the one closest to exactly that horizon.

src/glue/gold_features.py — one line that matters

silver.where(F.col("service_date") < F.lit(RUN_DATE).cast("date"))

Strictly earlier. Include today and the label leaks into the features; every metric reported afterwards is fiction. A test MAE under ~40 seconds is the tripwire that says this has happened.

War stories

Twelve bugs, four of them silent

The interesting half are the ones that don't raise an error. A job that fails is a job you fix; a job that succeeds while producing nothing is one you ship.

WhatHow it failed
Athena partition projection vs SparkSilent. Projection is Athena-only. Spark asked the Glue catalog for partitions, got an empty list, read zero files, and reported SUCCEEDED in 73 seconds.
to_timestamp() on an epoch bigintSilent. Expects a string; would cast 1786479340, fail to parse it, and return NULL — nulling four temporal features while the job succeeded.
dim_trips column orderSilent. TransLink includes trip_short_name; the generic DDL didn't. OpenCSVSerde maps positionally and ignores names, so direction_id would have held trip names.
Kinesis write throttlingSilent-ish. ~21,000 records pushed in 4.5 s ≈ 2,400/sec against a 1,000/sec shard. Retries compounded, invocations failed, polls were lost to the DLQ.
Cross-region alarm actionsBilling metrics exist only in us-east-1, but the alarm targeted an SNS topic and Lambda in ca-central-1. CloudWatch rejects that outright.
Lambda reserved concurrencyNew accounts get a concurrency quota of 10, not 1,000. Reserving 2 dropped the unreserved pool below the enforced minimum.
Missing --enable-glue-datacatalogSpark used an empty local metastore and couldn't see a single table.
Iceberg timestamp typeAthena types the column as timestamp without timezone; Spark's Iceberg connector refuses it without an explicit opt-in.
Hourly ETL schedule72 Glue job runs a day ≈ $150/month for training data consumed by a weekly retrain.
One-line .gitignoreWould have published the API key to a public repo on the first commit.

The throttling fix is the best story. The obvious answer is a second shard, at $11/month. But the function had a 120-second timeout and was finishing in 4.5 seconds — the capacity was already paid for. Pacing PutRecords to 900/sec pushed duration to 23 seconds, took throttling to zero, and cost nothing. Dropping memory from 1 GB to 512 MB afterwards was free, because a function that spends most of its life asleep doesn't need CPU.

Questions you will be asked

Walk me through the hardest bug.

Partition projection. The Athena tables compute partitions from a formula instead of registering them in the catalog — no crawler, no MSCK REPAIR, no crawler cost. But projection is an Athena feature, and Spark doesn't implement it. Two engines reading the same table definition: Athena found 1.5 million rows, Spark found zero and reported success. The fix was reading the S3 prefix directly, since Firehose writes a deterministic path.

How do you know the model is any good?

Three baselines computed on the same held-out rows: the published schedule, persistence, and the historical median for that route/stop/hour. The split is time-based, never random. And a registry gate rejects any model that doesn't beat persistence by 8% — a gate that always passes is decoration.

Why no EC2?

The workload is bursty and scheduled, so paying for idle capacity buys nothing. A t3.medium idling all month is roughly the entire budget, spent sitting between one-minute polls. Everything is serverless or ephemeral — SageMaker training rents an instance for seven minutes and destroys it.

How do you control cost?

Concrete, not philosophical: a billing alarm invokes a Lambda that disables the ingestion schedule. Also no NAT Gateway — the only component needing internet is the poller, and an unattached Lambda has internet for free, so two free gateway endpoints replace a $32/month appliance.

What would you do differently?

Write the training/serving parity test in week two rather than week six. And measure feed volume before sizing the stream — the guide's estimate was 4M rows a day; the real number was 16M, which is what caused the throttling.
